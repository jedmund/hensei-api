# W10: correctness on the build

**Wave 4.** Depends on W8 (the build is prod's only writer since #575). Migration block `…19xxxx` (`…18xxxx` is left for W9's fixtures). Issue label `pipeline:W10`.

## Branches, CI and data

The same setup as W8:
- **PRs:** target `pipeline/integration`, where CI doesn't run. Paste the full local suite result in the PR body. The lead merges.
- **To `main`:** one linear "rebase and merge" PR per batch.
- **Catalogue:** the newest `catalogue-*-w8` (or later) release, restored with `bin/setup-pipeline-db <name> <tag>`. Never `hensei_dev`.
- **Wiki:** never fetch from it. Evidence comes from `weapon_sources` or an in-game capture.

## Rules for every change

- **Where the fix lives:**
  - **Compiler:** a fix to the build (`lib/weapon_skills/build/**`). Bump `Build::VERSION` when the output changes, so every weapon goes stale and rebuilds on the next deploy.
  - **Overlay:** a cited entry in `data/weapon_skill_curation/<series>.json`.
  
  Never a one-off data migration.
- **The baseline:** each PR refreshes it (`granblue:skill_parity write=true` after a full `build_weapon_skills all=true mode=write`). The PR lists every changed version with its evidence, in the style of `docs/weapon-skill-pipeline/w8-baseline-refresh.md`. The user reviews value changes.
- **Goldens:** every available golden spec stays green. An item marked **needs golden** waits for its W9 recapture. Its expected panel values come from the capture, never from a guess.
- **Determinism:** two full builds in a row are identical, and a second write changes nothing.
