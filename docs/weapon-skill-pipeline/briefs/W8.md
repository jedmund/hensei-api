# W8: build, shadow, switch

**Wave 3.** Depends on waves 0–2, all on `main` since #560. Migration block `…17xxxx`. Issue label `pipeline:W8`.

**Team:** the lead and up to three parity agents. The gates below are sequential; parity agents join at gate 2.

## Branches, CI and data

- **Branches:** work branches start from `pipeline/integration` (`pipeline/W8-<topic>`), and their PRs target `pipeline/integration`. CI doesn't run on PRs into that branch, so run the full suite locally (`DATABASE_URL=…_test bundle exec rspec`) and paste the result in the PR. The lead merges.
- **To `main`:** one PR from `pipeline/integration` per deploy gate (gate 3 shadow, gate 4 write). That's where CI runs.
- **Catalogue:** `catalogue-20261015-prod`, prod after the waves 0–2 deploy and its runbook. It includes `weapon_sources`, Regus (`1040906500`), Subekuri Gauntlet, the 67 rebuilt versions and the per-version descriptions. Restore it with `bin/setup-pipeline-db <name> catalogue-20261015-prod`.
- **Wiki:** never fetch from it. Every input is in `weapon_sources`; read it through `WeaponSkills::SourceStore::Database` / `Granblue::Parsers::Wiki.offline`.

## Goal

One deterministic build owns every generated weapon-skill row:

```
stored sources ──▶ Structure ──▶ overlay structural ops ──▶ Rows ──▶ Writer ──▶ overlay sync
```

The old writers are deleted at the end: `WeaponParser`'s skill persistence, `ExpandedWeaponSkillImporter`'s repair and notes, and `WeaponSkillDescriptionExtractor`. Corrections live only in the curation overlay.

## Decided

- **Gameplay notes:** compile from every expanded page (all 703), as today. Narrowing to series templates is a later, separately reviewed change.
- **`scales_with_skill_level`:** derived in the build from the version's frame. A version that resolves a family curve scales; anything else doesn't.
- **Tier text:** `Version#description_en/jp` comes from the Structure compiler's own tier text. `TierText` stops calling `WeaponParser#build_skill_entry`, so the old parser can be deleted.
- **Baseline:** refreshed once, at the end of gate 2, with every intended change listed in that PR. It's deleted after the switch and the W9 golden recaptures, not in W8.

## Gate 1: wire the build (lead)

1. **`WeaponSkills::Build.for(weapon, store:, overlay:)` → `BuildResult`:**
   - `Structure.call`;
   - the overlay's structural ops: `remove_version`, `add_version`, `gate`, `description`;
   - per version: tier text, family backfill (`Rows::Classification.backfill`), and `Rows.call` with the weapon's `CurationView` and parsed gameplay notes;
   - `BuildResult#validate!`.
   
   It is pure: no database writes, no network.
2. **`WeaponSkills::Build::Writer`.** It writes one `BuildResult` in a transaction, upserting by identity:
   - **Ids survive rebuilds:** versions keep their ids.
   - **Generated rows** are replaced. Curated rows (`manually_edited_at` set) are never touched, and suppressed boost types are never written.
   - **Override columns** (`*_override`, `suppressed_boosts`, `overrides_edited_at`) belong to the overlay, so the writer leaves them alone.
   - **Gone versions and slots:** a version or slot missing from the build is deleted, unless a curated row hangs on it. In that case, report it and keep it.
   - Then the overlay sync runs for the weapon as it does today.
3. **Keys:** `KeySkillExtractor` (W5) stays its own step, after the weapons, reading the store.
4. **`granblue:build_weapon_skills [ids=] [series=] [all=true] [mode=shadow|write]`**
   - `shadow` builds inside a rolled-back transaction and prints `ParityReport` grouped by series.
   - `write` keeps the result.
   - Without `all=true`, only weapons whose fingerprint changed are built. A fingerprint hashes:
     - the weapon's source `sha256`s;
     - its overlay entries;
     - `Build::VERSION`, bumped when compiler output changes.
     
     Store it per weapon (a small table or column, migration `…1700xx`).
5. **Deploy hook:** after the curation sync in `db:migrate:with_data`, run the build in `WeaponSkills.build_mode`.
   - `off`: does nothing.
   - `shadow`: logs a summary per series plus the first 50 differences, and **never fails the deploy**.
   - `write`: builds the stale weapons.

**Acceptance:**
- **Specs:**
  - `Build.for` for each page kind (inline, series template, key-determined);
  - a second `write` changes nothing;
  - curated rows and overrides survive a rebuild;
  - shuffled source order gives the same result;
  - a WebMock spec shows no HTTP.
- **Determinism:** `build_weapon_skills all=true mode=shadow` on a fresh `catalogue-20261015-prod` restore runs twice with identical output.

## Gate 2: parity loop (lead + parity agents)

- **The work:** run the shadow build over everything and diff it against the baseline (`granblue:skill_parity`, `group=series`).
- **Claiming:** each agent claims a set of series on the W8 issue. They fix compiler bugs in the W6 files (say which on the issue first; two agents never edit one file at once) or add overlay entries in their own series' files only.
- **Intended differences:** each must cite its classification doc: `w2-classification.md`, `w6a-classification.md`, `w5-classification.md`, or W6b's `compare_rows_classifications.json`. The ones already known:
  - 28 new tiers. This includes Rhomphaia's upgraded tiers, so its 4 waiting curation entries finally match.
  - 12 Revans Mk II skills gated at 120/4/0.
  - Gun Voltage II moves slot.
  - 8 hatnote sizes.
  - 12 Enforcement junk versions dropped.
  - 5 Sephirath levels.
  - 2 false Astral Arts links.
  - Colomba's redundant Voltage row; Blazing Chain III's `cb_amp` 50.
- **Done when:**
  - every remaining difference is intended and cited;
  - two consecutive full builds are identical;
  - `compare_structure` and `compare_rows` report no unknowns.
  
  The lead then refreshes the baseline in one PR that lists the intended changes by series, for the user to review.

## Gate 3: prod shadow (lead, then the user)

- **PR into `main`:** `pipeline/integration` → `main`. Once it's deployed, the user sets `WEAPON_SKILL_BUILD=shadow` on the Railway API service and redeploys.
- **Acceptance:** the shadow summary in the deploy log matches the refreshed baseline's intended changes and nothing else.
- **If not:** an unexpected difference means prod differs from the catalogue. Classify it in gate 2 terms, fix it, and shadow again.

## Gate 4: switch (lead)

- **Flag:** `WEAPON_SKILL_BUILD=write`, set by the user on Railway.
- **Route through the build:**
  - `EntityReparser` for weapons;
  - the admin weapon reparse and fetch-wiki endpoints;
  - `SourceStore::Fetcher#record_followed_pages`, which records followed pages by running `Structure` against a `Recording` store instead of `WeaponParser`.
- **Delete:**
  - **tasks:** `parse_weapon_skills`, `extract_weapon_skill_descriptions`, the repair half of `refetch_expanded_weapons`, `backfill_weapon_skill_sizes`, `recover_july_reparses`;
  - **code:** the old classes' skill-writing code;
  - **`durability_check`:** replaced by `skill_parity` plus the goldens.
- **Old data migrations** that call a deleted class: guard them so they do nothing when the class is gone. They've already run on prod.
- **Redundant overlay ops:** retire the 95 that the build now reproduces (`compare_structure` lists them).

**Acceptance:**
- The prod `write` deploy leaves `skill_parity` against the refreshed baseline at zero.
- The drift check is clean.
- The golden specs pass.
